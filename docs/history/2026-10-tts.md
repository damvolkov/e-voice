# 2026-10 · TTS: backend choice and first measurements

Decisions taken when the TTS service was built (2026-10-02), the evidence behind them, and what was
measured on the workstation (i9-14900K, 32 threads, 188 GB, CPU only).

## Requirements

- Rust service beside STT, same philosophy: abstract ports, backends behind a registry.
- Real streaming only: audio must leave while a sentence is being generated (voice agents, barge-in).
- Spanish (Spain) and English; voices that sound like a given speaker; fast on CPU.
- A `train` in the port, empty or not per backend; model training stays Python, model-side only.

## Pocket TTS, and why not through sherpa-onnx

Kyutai Pocket TTS (100M, CALM: a causal transformer proposes one continuous Mimi latent per 80 ms frame,
a one-step consistency head samples it) has Spanish since 2026-05, zero-shot cloning, MIT code and
CC-BY-4.0 weights (gated, no cloning without consent).

sherpa-onnx 1.13.8 was the obvious host, and it does not fit:

- only the January English checkpoint is converted; newer exports (Spanish included) fail to load
  (k2-fsa/sherpa-onnx#3755: fp16 KV states, missing `bos_before_voice`);
- its loop generates every latent of a sentence before decoding, so the first audio waits for the whole
  sentence, and cancellation is only checked between decoder chunks;
- a fine-tuned checkpoint cannot be loaded.

So Pocket runs on our own loop on `ort` over `lomotron/pocket-tts-onnx-export@8f52199` bundles (five
graphs: text conditioner, Mimi encoder, FlowLM backbone with explicit KV state, stateless flow head,
stateful Mimi decoder). The published Spanish bundles were stale (weights changed 2026-10-01, tokenizer
2026-09-24), so the export is ours: `make pocket`. The Rust loop reproduces the Python reference loop on
the same bundle to < 1e-3 (golden test), and its output matches upstream torch: both end the same long
sentence at the same comma. That early end is the model's; cutting sentences at 80 chars (clauses first)
keeps every clause.

Voices: a voice stores the prepared prompt (≤ 30 s, trailing silence trimmed), not a model state, so it
survives model changes; the encoder runs when a stream opens and is cached per voice and model. Pocket
without a prompt produces noise, so opening without a voice is refused.

## Alternatives (for the next backends)

Surveyed 2026-10-02 against the streaming requirement:

| Model | Verdict |
|---|---|
| Qwen3-TTS 12Hz 0.6B (Apache-2.0) | **next, quality**: Spanish WER 1.49 / SIM 0.81 published, dual-track streaming with a causal codec (320 ms packets), zero-shot cloning, fine-tune scripts. CPU is the risk: ≈ RTF 1 on 4 vCPU in a hand-tuned C engine, ORT ≈ 2× slower. Split ONNX graphs exist (wavekat); streaming with cloning must be built. |
| NeuTTS Nano Spanish (117M active) | **next, light**: autoregressive on a 50 Hz codec, 0.5 s windows, cloning; quality likely on par with Pocket; custom licence to read; backbone is GGUF (needs ONNX to stay on `ort`). |
| Chatterbox Multilingual es-es | best Castilian fit; RTF ≥ 4 on CPU even in ggml — rejected |
| Supertonic 3, Kokoro, Piper, Matcha, MeloTTS | sentence at once — fail the streaming contract |
| CosyVoice 3, VoxCPM 2, Orpheus, Higgs, Index-TTS | GPU-class |
| XTTS v2, F5-TTS, Fish/OpenAudio, Voxtral TTS | non-commercial weights |

## Measurements

`make bench SERVICE=tts`, 40 FLEURS sentences per run (8–18 s of speech each), voice learned from a 20 s
sample, `tts.text.max = 80`. TTFA is request to first audio, voice priming included.

| Config | Streams | TTFA p50 | RTF p50 | Throughput | CPU s / audio s |
|---|---|---|---|---|---|
| base int8, 2 threads | 1 | 158 ms | 0.33 | 3.0× | 0.44 |
| base int8, 2 threads | 4 | 257 ms | 0.64 | 5.8× | 0.85 |
| base int8, 2 threads | 8 | 436 ms | 1.24 | 5.8× | 1.73 |
| base int8, 4 threads | 1 | 155 ms | 0.32 | 3.1× | 0.53 |
| base fp32 | 1 | 259 ms | 0.46 | 2.2× | 0.68 |
| large (24 layers) int8 | 1 | 558 ms | 0.96 | 1.0× | 1.22 |

Readings:

- One stream speaks 3× faster than real time with first audio in ~160 ms (≈ 70–120 ms once the server
  holds a warm stream); English matches Spanish.
- Aggregate throughput stops at ~6× real time from 4 streams on: memory bandwidth, not cores. The
  exported backbone copies its whole 1000-position KV cache (≈ 49 MB for 6 layers) in and out on every
  80 ms frame. **Next:** re-export with a shorter static cache (≈ 576 positions with prompts ≤ 20 s) and
  measure again.
- More threads per stream buy nothing; int8 is 1.4× faster than fp32; large is real time on one stream
  only.

Quality, second pass (round-trip WER: Parakeet transcribing the synthesized audio, accent-folded;
similarity: WeSpeaker ResNet34 cosine to the 20 s sample):

| Config | WER es | WER en | Similarity es | Similarity en |
|---|---|---|---|---|
| base int8 | 9.9 % | 13.6 % | 0.69 | 0.72 |
| base int8, 4 threads (same model, another sampling) | 12.9 % | 15.6 % | 0.69 | 0.72 |
| base fp32 | 9.8 % | 12.1 % | 0.71 | 0.74 |
| large int8 | 7.2 % | — (English stays on base: 10.7 %) | 0.70 | 0.72 |
| real speech, same texts (Parakeet) | 4.5 % | 8.1 % | | |

The two base int8 rows are the same model: sampling at temperature 0.3 alone moves Spanish WER by 3
points on 40 items. Raw results: `data/tts/ops/results/` (`make report SERVICE=tts`). See also
[the benchmark page](../benchmark.md#tts).

## Second round (2026-10-03): Qwen3-TTS and NeuTTS

Qwen3-TTS 12Hz 0.6B joined on our own talker / code-predictor loop over wavekat's ONNX graphs
(`wavekat/Qwen3-TTS-0.6B-Base-ONNX@177cd39`, int4 talker and predictor, causal vocoder on its own thread).
Its preprocessing is checked against the official code (mel, x-vector, reference codes, tokenizer, text
projection). Same voice, 40 sentences per language:

| | Pocket base | Qwen3 |
|---|---|---|
| WER es / en | 9.9 / 13.6 % | 8.2 / 16.4 % |
| similarity es / en | 0.69 / 0.72 | 0.74 / 0.74 |
| first audio (p50) | 161 ms | 380 ms |
| RTF, 1 / 4 / 8 streams | 0.35 / 0.82 / 1.23 | 0.96 / 2.0 / 3.7 |
| throughput, 1 / 4 / 8 streams | 2.2× / 3.2× / 4.8× | 1.0× / 1.7× / 1.8× |

- Per frame the 15-call code predictor costs ≈ 40 ms (4 threads) and the talker ≈ 14 ms; the fp32
  predictor is 3× slower (memory-bound), so int4 stays. Overlapping the vocoder gained little.
- In-context cloning with a 20 s reference was worse than the x-vector (similarity 0.71 vs 0.76 on 20
  sentences) and much slower; it is used only for clips ≤ 10 s with their transcript.
- The streaming contract now bounds the first chunk (≤ 500 ms) separately from later ones (≤ 2 s): a
  vocoder that needs left context voices several frames at once without delaying first audio.

NeuTTS Nano is implemented (phonemizer over espeak-ng, GQA backbone loop, `NeuCodec` windows with
overlap-add) and runs in tests on stand-in graphs with its exact IO; the real weights are gated by
neuphonic and await accepting their terms (and `espeak-ng` on the host).

The workspace moved under `evoice/` (`evoice/core`, `evoice/stt`, `evoice/tts`); `cli/`, `eval/`,
`docker/`, `docs/` and `data/` stay at the root.
